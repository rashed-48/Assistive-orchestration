01

What the system is

A person speaks. The system decides what has to happen in the physical environment to satisfy that request from where things currently stand, then carries it out across distributed devices and records only what the hardware confirmed.

The distinguishing property is in the second step. A conventional voice-controlled home maps an utterance to a fixed command or a fixed script. This system treats the utterance as a goal and derives the action sequence from the current logical world — so the same sentence produces different work depending on the state of the house.

The claim, stated precisely

# A fixed-script system
intent  --------------------------------->  fixed action list

# This system
intent + current state + topology + device dependencies  -->  required action list

Measured across the implemented system: 48 (intent, starting-state) pairs produce 43 distinct action sequences. A fixed-script design over the same 8 movement intents would produce 8.

04

The dependency scheduler

This is the core of the framework. "Scheduler" here means dependency resolution, not time: nothing in the system is triggered by a clock, a calendar or a timer.

4.1 The scheduling function

W = f( I, S, T, D, P )

  I  intent                  one of 11 supported goals
  S  current logical state   room, mode, location certainty, every device
  T  topology                which rooms connect, through what
  D  device dependencies     a room must be lit before it is used, a door
                             opened before it is passed, a room closed on exit
  P  policy                  emergency latch, location certainty guard

  W  ordered action sequence

And the state advances only on confirmation:

S(t+1) = F( S(t), W, ACK )   # no ACK, no state change
What this is, technically A hand-specified, state-conditioned transition expander. There is no search, no goal representation and no declarative precondition language — preconditions are expressed as conditionals over the state, and ordering is implicit in the emitted sequence. It is closer to a parameterised finite-state machine than to a classical task planner, and the document describes it that way deliberately.

4.3 Topology

4.4 The corridor invariant

The most instructive dependency rule in the system, because it is conditional in both directions:

  • The corridor light is raised before the destination door opens — and only if the corridor is genuinely traversed.
  • It is lowered after arrival — and only if it was raised.
  • If the person is already in the destination, no corridor action is emitted at all.
  • If the person is standing in the corridor and it is already lit, no redundant command is sent.

All 6×4 combinations of source and destination are enforced by 120 automated tests.

State model & commit semantics

5.1 What the state holds

FieldMeaning
current_roomLast committed location of the person
location_statusKNOWN · IN_TRANSIT · UNKNOWN — how far current_room can be trusted
location_destinationWhere an in-progress move is heading
location_reasonWhy certainty was lost, for the operator

5.2 Two commit tiers

The system commits at two different granularities, and the distinction matters for correctness under failure.

Per acknowledged action

Device state. A light is recorded ON the moment its node confirms it. Ten actions, ten small commits.

Per completed workflow

Room, mode, return target, location. Committed only once every action in the plan has been acknowledged.

The consequence is deliberate: a workflow that fails part way leaves the devices it actually moved recorded as moved, and does not claim the person arrived.

5.3 What counts as an acknowledgement

# All four must hold before any state moves
result is a mapping
result["status"] == "success"
result["device"] == the device we commanded
result["action"] == the action we sent

A timeout, a device-reported error, a malformed reply, or a reply about a different device all leave the logical state untouched.

06

Location certainty

The system has no sensors. It cannot see where the person is; it can only remember where it last successfully sent them. This section is about being honest about that.

The interruption rule

When a movement workflow fails part way, the system decides what it can still honestly claim using a physical argument:

No door was opened

The person cannot have left. The source room is still true, so the location stays KNOWN. A failed light does not trigger a dialogue.

A door was opened

They may be anywhere along the route. The only honest answer is UNKNOWN, and movement commands are refused until a human resolves it.

Why this matters more once state is durable Without persistence a stale location lives only as long as the process. Once state survives a restart, a location the system cannot vouch for becomes a durable false claim — and every future plan would be built on it.
07

Reliability & safety envelope

7.1 Exactly-once physical execution

A retry exists because an acknowledgement did not arrive — not because the action did not happen. The system is built around that distinction.

# One logical action = one identity, reused across all attempts
attempt 1  ->  command_id = 4b45c942…   (no ACK)
attempt 2  ->  command_id = 4b45c942…   (node recognises it)
attempt 3  ->  command_id = 4b45c942…

# Node side: 128-entry history of completed command ids
duplicate id  ->  re-acknowledge, do NOT actuate

Verified end-to-end against a live broker: an acknowledgement was dropped, the executor retried, and the door opened once.

7.2 Emergency lifecycle

StageBehaviour
EntryMode latched before any hardware is touched — a partly failed alarm is still an emergency. Buzzer raised, exit and all internal doors opened.
Held openNothing closes the escape route. Entry emits no CLOSE_DOOR at all.
While latchedAll ordinary intents refused. Only EMERGENCY (idempotent retry) and EMERGENCY_CLEAR are accepted.
Best effortA failed door does not abandon the remaining doors; failures are reported, not swallowed.
ClearConfirmed command silences the buzzer and closes up. If any required action fails, the latch holds.
Across restartLatch restored from durable evidence. No actuator is re-fired — a stored file is not proof the buzzer is sounding.
A design decision worth stating explicitly Entry deliberately does not close the doors it opens. In an earlier revision it did, and the escape route was measured open for 7 milliseconds. The software cannot know whether anyone got out, so the route now stays open until a human says otherwise.

7.3 Medication

Twelve of the thirteen action types are set-to-a-state operations and converge on repetition. ACTIVATE_MEDICATION is an impulse — it dispenses a dose. It is recorded in the audit log and never replayed; no replay mechanism exists anywhere in the system.

08

Persistence & restart recovery

8.1 What is stored

Snapshot — state.json

The whole world plus metadata. Written atomically: temp file → flush → fsync → os.replace. Previous copy kept as .bak.

Event log — events.jsonl

One line per acknowledged action: timestamp, intent, device, action, command_id, node, status, resulting state. An audit trail, never a replay queue.

{ "schema_version": 1,
  "application_version": "0.10.0",
  "saved_at": "2026-08-27T04:49:49Z",
  "clean_shutdown": false,
  "state": { … the full environment … } }

8.2 How far a restart trusts what it finds

Stored statusPrevious exitRestored asReasoning
KNOWNcleanKNOWNNothing happened in between that could have been missed
KNOWNcrash, nothing committedKNOWNThe stored world is identical to a fresh one — no claim to distrust
KNOWNcrash, after real workUNKNOWNThe session ended mid-life; the location may be stale
IN_TRANSITanyUNKNOWNThe move never completed; both endpoints retained for diagnosis
UNKNOWNanyUNKNOWNUncertainty is never laundered into a room

The clean-shutdown marker is written dirty at startup and set true only by an orderly shutdown, so an abandoned process cannot masquerade as a clean exit.

The defect this closed Before persistence, restarting the application silently cleared an active emergency: a fresh state object reported mode NONE and accepted ordinary commands again. A restart was, in effect, an unauthenticated emergency clear.

9.3 Limitations — stated plainly

No physical hardware

All three nodes are software. Nothing in this document has been demonstrated on a real ESP32 or a real door.

No comparative evaluation

495 tests establish correctness against a specification. They do not establish that the specification is better than an alternative design.

No sensing

All 16 devices are actuators. Logical state is what the software believes after a confirmed command, never a measurement.

Single writer

Two application instances sharing one state directory would interleave writes. This is documented, not solved.

9.4 What the framework does not claim

MQTT, ESP32, publish/subscribe, speech-to-text, sentence embeddings, retries, command identifiers, write-ahead logging and atomic file replacement are all standard, established technology. The framework's contribution — if any — lies in how the state, uncertainty and safety semantics are composed around them, and that composition has not yet been evaluated against a baseline.
